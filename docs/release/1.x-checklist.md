# Orchestra 1.x release checklist

This checklist separates technical release readiness from operator-authorized external mutations. The Release Train automates mechanics; it does not remove the operator gate.

## Technical gate

- [ ] Schema validators regenerated and `check:schemas` clean.
- [ ] Runtime images regenerated and `check:runtimes` clean.
- [ ] Runtime manifests complete and version-coherent.
- [ ] Shared manifest project manager install/update/dry-run/rollback contract green.
- [ ] Installed Codex and Antigravity runtimes pass self-contained smoke tests without source-checkout imports.
- [ ] Dream and Jev Labs declare `authority = NONE` and authority tests are green.
- [ ] Manifest-driven Doctor reports healthy.
- [ ] Cross-runtime contamination and firewall checks are green.
- [ ] Direct Work and Work Lease suites are green.
- [ ] Full `npm test` regression is green.
- [ ] Release Train contract tests and release-readiness check are green.
- [ ] Independent whole-branch review/security review has no unresolved blocker.

## One-time repository prerequisite

The repository must allow its `GITHUB_TOKEN` to create pull requests: **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**.

If this permission is unavailable, `Prepare Release` fails without publishing and removes the release branch it just created, so enabling the setting and rerunning does not require branch cleanup.

GitHub may place `pull_request` workflows created by `GITHUB_TOKEN` into an approval-required state. The Release Train does not rely on that run for publication authority: `Prepare Release` executes the full prepared-release preflight before opening the PR, and publication later requires canonical `CI` success on the exact merged `main` SHA.

## Rollback readiness

- Direct Work lever documented: `ORCHESTRA_DIRECT_WORK_MODE=off|shadow|on`.
- Authority lever documented: `ORCHESTRA_AUTHORITY_MODE=session|dual|lease`.
- Runtime update/rollback preserves declared project state and user `.git/info/exclude` entries.
- Stale lease generations remain fail-closed.

## Operator approval required

Stable version publication remains operator-gated.

1. Open **Actions → Prepare Release**.
2. Explicitly choose `patch`, `minor`, or `major`.
3. Review the generated `release/vX.Y.Z` pull request, including the requested bump, advisory Conventional Commits suggestion, generated release notes, version-source changes, generated runtime artifacts, and prepared-release preflight evidence.
4. If the release is approved, merge the release PR using GitHub's **Create a merge commit** option. Squash and rebase are not valid release authorization methods.

**Merging the release PR as a merge commit is the explicit operator authorization to publish that version.**

The preparation workflow must not create tags or GitHub Releases.

## Automatic publication after approval

After the release PR merge:

- canonical `CI` must succeed on the exact resulting `main` SHA;
- the publisher must prove that exact SHA is associated with the merged `release/vX.Y.Z` PR;
- the exact SHA must be a two-parent merge commit;
- an existing tag must either be absent or already resolve to the exact release integration SHA;
- the publisher creates an annotated tag and GitHub Release automatically;
- release notes are augmented with the exact `main` SHA and CI run URL;
- a rerun is idempotent: existing correct tag + missing release publishes only the release, while existing correct tag + existing release is a no-op;
- any tag conflict fails closed.

Ordinary successful `main` CI runs must not publish a release. When the current version has no generated `docs/release/vX.Y.Z.md` candidate, publication is a no-op.

Manual tag or GitHub Release creation is reserved for explicit recovery, not the normal release path.
