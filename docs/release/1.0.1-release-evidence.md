## Triggering defect

The v1.0.0 official Codex installer correctly used the manifest-driven project runtime manager and wrote canonical schema-v2 metadata to:

`.orchestra/state/runtimes/codex.json`

However, the source-level Codex lifecycle command still delegated Doctor/update behavior to the legacy provider-local runtime manager, which expected:

`.codex/orchestra-runtime.json`

As a result, an intact official v1.0.0 installation could not obtain a green source-level Doctor. The equivalent split was subsequently reproduced for the Antigravity source lifecycle.

Windows verification also exposed independent portability defects involving Bash-only Doctor invocation, POSIX executable-bit assumptions, CRLF-sensitive generated-schema freshness, path-separator-sensitive firewall assertions, and platform-specific file modes in deterministic runtime-build metadata.

## Corrected contract

Current source-level Codex and Antigravity lifecycle commands use the manifest-driven v2 project-runtime contract.

Canonical metadata locations are:

- Codex: `.orchestra/state/runtimes/codex.json`
- Antigravity: `.orchestra/state/runtimes/antigravity.json`

Current source-level lifecycle commands do not create or require legacy provider-local metadata such as `.codex/orchestra-runtime.json` or `.agents/orchestra-runtime.json`.

The provider Doctors now validate an installed project against the same deterministic runtime payload produced by the official builder. They verify installation presence, v2 metadata, managed-runtime integrity, and metadata freshness.

Provider-specific quiescence remains fail-closed through v2 adapters. Active runtime state prevents update unless the operator explicitly uses the existing force recovery path. Managed-runtime drift remains unhealthy rather than being silently normalized.

Legacy provider-local lifecycle modules remain in the runtime only for compatibility/recovery and existing invariant coverage; they are not the canonical current source lifecycle.

## Windows and Linux portability

The CI workflow now contains a permanent portable-runtime matrix for both `ubuntu-latest` and `windows-latest`.

The portable lane covers:

- official provider install;
- immediate source-level Doctor;
- v2 update/no-op behavior;
- active-state mutation fencing;
- managed-runtime drift detection;
- runtime-builder determinism;
- runtime distribution build;
- general Orchestra Doctor.

Additional portability corrections include:

- `npm run doctor` invokes Node directly instead of requiring Bash;
- POSIX executable-bit preservation remains validated only on filesystems where that semantic exists;
- generated schema freshness treats CRLF checkout conversion as content-equivalent;
- diagnostic path assertions normalize Windows separators without weakening firewall policy;
- `orchestra-runtime-build.json` no longer serializes platform-specific file modes, while the builder still preserves executable permissions during POSIX copies.

After `v1.0.1` is published or the operator deliberately chooses the verified `main` source, the intended downstream validation is:

1. run a dry-run update against Tsuzuki;
2. update the installed Codex runtime through `scripts/orchestra-codex-project.mjs`;
3. confirm canonical v2 metadata remains authoritative;
4. confirm no legacy `.codex/orchestra-runtime.json` is created;
5. run the source-level Codex Doctor and require `HEALTHY`;
6. confirm tracked Tsuzuki project state remains unchanged except for intentionally managed Orchestra runtime state.
